# ROCm 7.14.0rc1 amdsmi asset sync + amdsmi-sync-assets fixes

- **Date:** 2026-07-07
- **Author:** praveen
- **Related PR(s):** #1440
- **Related issue(s) / JIRA:** follow-up to #1432

## Context

PR #1432 bumped `ROCM_TARBALL_URL` to the ROCm 7.14.0rc1 therock tarball but did not run
`amdsmi-sync-assets`, leaving `assets/amd_smi_lib/` with stale rc0/nightly binaries. Three
additional issues were found while fixing this:

1. `amdsmi-from-tarball` did not extract `librocm_sysdeps_*.so*` from the tarball, so sysdeps
   were never refreshed via the tarball sync path.
2. `amdsmi-sync-assets` did a blanket glob copy of all sysdeps, risking untracked files
   accumulating silently on each update.
3. `UBUNTU22/lib` and `UBUNTU24/lib` under `assets/amd_smi_lib/x86_64/` were duplicates of
   RHEL9 content, requiring manual sync on every update.

## Approach

- Fix `amdsmi-from-tarball` (`Makefile.compile`): add `librocm_sysdeps_*.so*` to the tar
  extraction wildcards so sysdeps are staged alongside `libamd_smi.so*` and `amdsmi.h`.
- Fix `amdsmi-sync-assets` (`Makefile.compile`): scope sysdeps copy to only files already
  present in `dest/` (loop over existing tracked files, not a blanket glob). Add `version.txt`
  update at the end of the sync so it is always kept in sync atomically.
- Sync RC1 assets: run `make amdsmi-sync-assets AMDSMI_TARBALL_FORCE=1` to refresh
  `amdsmi.h`, `libamd_smi.so.26.5.0`, and the 5 tracked sysdeps from the RC1 tarball.
- Replace `UBUNTU22/lib` and `UBUNTU24/lib` real directories with symlinks to `../RHEL9/lib`.
  Both directories held identical content to RHEL9 (same tarball source). The symlinks
  eliminate duplicate maintenance — any future `amdsmi-sync-assets` run updates all three
  OS variants automatically.

### Alternatives considered

- **Symlink at UBUNTU22/ directory level (not lib/)** — rejected; would remove the UBUNTU22
  directory itself which may confuse build scripts that iterate `x86_64/*/`.
- **Add new sysdeps to tracked files** — deferred; the set of sysdeps needed at runtime is
  intentionally conservative. New sysdeps should be added explicitly when a runtime need is
  confirmed, not automatically on every tarball update.

## Scope

- **In scope:** `Makefile.compile` fix, RC1 asset sync (RHEL9 only), UBUNTU22/24 symlinks,
  `version.txt` automation.
- **Out of scope:** UBUNTU22/UBUNTU24 libdrm updates (populated by the source-build path,
  not the tarball sync path); adding new sysdeps beyond the 5 currently tracked.

## Validation

- `make docker AMDSMI_FROM_TARBALL=0` succeeded with the updated committed assets.
- Deployed to single-GPU test host (AMD Radeon Graphics) via DeviceConfig CR patch.
- `/metrics`: 88+ metrics served with non-zero values.
- `rocpctl`: no linker errors, all 28 shared libs resolve cleanly.
- `amd-smi metric` (inside container) vs `/metrics`: exact match on power/clocks/VRAM;
  ±1 °C on temperatures (scrape interval jitter only).

## Risks and rollback

- `UBUNTU22/lib` and `UBUNTU24/lib` now resolve to RHEL9 content via symlink. If a future
  Ubuntu-specific docker target is added, it will pick up RHEL9 libdrm versions. Rollback:
  remove symlinks and restore from git history (`git checkout HEAD~1 -- assets/amd_smi_lib/x86_64/UBUNTU{22,24}/lib/`).
- Sysdeps copy is scoped to the 5 currently tracked files. Adding new sysdeps requires an
  explicit `git add` — this is intentional to prevent accidental bloat.
