## Findings (require follow-up beyond GPUOP-723)

**F1 — `gpuagent_static.bin.gz` shipped instead of `gpuagent_ual.bin.gz`:**
The whole point of GPUOP-723 is "container ships IFOE field exporter by default." But `docker/build_prep_docker.sh:43` (the default else-branch) extracts `assets/gpuagent_static.bin.gz` into the build context — that's the non-IFOE prebuilt gpuagent. The UAL gpuagent at `assets/gpuagent_ual.bin.gz` (built/staged by `scripts/update_ual_assets.sh`, used by deb/rpm IFOE packages) is NOT used by the container build. For the GPUOP-723 design to deliver its stated goal, build_prep_docker.sh needs an `IFOE=1` mode (or equivalent default for the IFOE-enabled container) that uses `gpuagent_ual.bin.gz`. Without this, `ENABLE_IFOE=true` is wired but never has an IFOE-aware gpuagent to talk to. Suggest a follow-up Sub-task on GPUOP-723 (or a new Story under GPUOP-722).

**F2 — libamd_smi 26.3.0 ABI compatibility with the bundled prebuilt gpuagent:**
The non-IFOE prebuilt `gpuagent_static.bin.gz` may have been compiled against libamd_smi 26.2.x. Bumping to 26.3.0 (commit `03f76cbc2` per design D4) appears to break it — the entrypoint-launched gpuagent goes defunct. Manual invocation works only because it inherits a slightly different env. This is independent of F1 but compounded by it: even if we ship the right gpuagent (F1), we should verify ABI compat across libamd_smi releases. The Story design's S7 (collapsed to TC09 LD_PRELOAD parity) gives us runtime symbol-resolution checks but not full ABI compat assurance.

**F3 — duplicate `entrypoint.sh` files (root vs `docker/`):**
The root `entrypoint.sh` is not referenced by any Dockerfile in the repo (all `ADD ./entrypoint.sh` in the docker/ Dockerfiles resolve to `docker/entrypoint.sh` because build context is `docker/`). The earlier GPUOP-735 commit edited the root file by mistake; commit `be50fa860` corrects this by editing `docker/entrypoint.sh`. The root file is now stale/dead code — recommend removing it in a follow-up cleanup.

**F4 — internal registry not reachable from this build host:**
`registry.test.pensando.io:5000` is configured as the default `DOCKER_REGISTRY` in `dev.env` but is not reachable from this build host. Workaround used for TC01: explicit `--build-arg BASE_IMAGE=registry.access.redhat.com/ubi9/ubi-minimal:9.6`. TC07/TC08 (libcopy-assets) have no equivalent override. This is environmental, not a GPUOP-723 bug.

## Verdict

**Story-test verdict: FAIL.**

P0 case TC03 (the foundational "graceful no-op" gate that lets the
single-image strategy ship safely) does not pass on the test host
because the deeper design gap F1 means the container has no IFOE-aware
gpuagent in the first place. P1 cases that depend on a live gpuagent
(TC09, TC11) are likewise blocked. The PASS results (TC01, TC04, TC05,
TC10) confirm the env / library / package-install side of GPUOP-735
is working — the gap is in which gpuagent binary is bundled.

**Recommendation:** Do not close GPUOP-723 yet. Triage F1 + F2 and add
a follow-up Sub-task (or new Story) to wire `gpuagent_ual.bin.gz` into
the container build, then re-run TC03/TC09/TC11 + the IFOE-rig TC02.

The amd-smi prefix grep fix (commit `e83b143f6`) was correct — TC03's
amd_ifoe count returns 0 here, which the test plan now distinguishes
from the legitimate "0 because gate suppressed" case via Step 5
(GPU metrics flow check). Both are 0 here, surfacing the gpuagent issue.
